📘 Metodología, Alcance y Comparativa Técnica con OWASP ZAP

Documento técnico y guía de sustentación sobre el funcionamiento interno del auditor DAST, los vectores evaluados y la complementariedad con el pipeline DevSecOps.

1. ¿Cómo funciona internamente nuestro script de auditoría DAST?

El script dast-audit-remote.mjs opera bajo el paradigma Grey-Box API Penetration Testing (Prueba Dinámica de Caja Gris con Contexto de Sesión) mediante el siguiente flujo automatizado:

  1. Ingesta de Especificación OpenAPI 3.0: Carga el archivo canónico docs/api/openapi.json que contiene el catálogo formal de 76 rutas y 105 operaciones REST del backend.
  2. Resolución Dinámica de Parámetros URI: Sustituye automáticamente variables de ruta ({slug}, {id}, {usuarioId}, {barberoId}) por identificadores reales del tenant auditado (barberia-demo-2).
  3. Inyección de Contexto Multitenant Zero-Trust: En cada petición HTTP propaga la cabecera x-negocio-slug, permitiendo que el middleware y el AsyncLocalStorage resuelvan la sede activa.
  4. Inyección de Sesión Criptográfica (Bearer JWT): Adjunta el token de sesión real del usuario autenticado (Felipe Armero [SUPERADMIN, BARBERO]), habilitando la inspección de endpoints privados.
  5. Fuzzing de Mutación Activa: En cada método POST, PUT y PATCH inyecta payloads maliciosos con caracteres hostiles de inyección (<'">) para verificar que el ValidationPipe intercepte los datos antes de la persistencia.
  6. Evaluación de Respuestas y Detección de Fugas: Analiza el código HTTP devuelto, calcula la latencia en milisegundos y confirma la supresión total de trazas de pila (Stack Traces) en respuestas de error.

2. ¿Qué evalúa exactamente el script? (Los 4 Pilares de Seguridad)

Pilar A: Inyección SQL y XSS (OWASP A03)

Verifica que payloads como ' OR '1'='1 -- y <script>alert(1)</script> sean neutralizados por el tipado estricto de Prisma ORM y los filtros DTO, arrojando 400 Bad Request y nunca errores no controlados (500).

Pilar B: Aislamiento Zero-Trust Multitenant (OWASP A01)

Valida el principio de Tenant Isolation: Si una petición lleva un token legítimo de la Barbería A pero intenta operar con la cabecera de la Barbería B, el JwtAuthGuard bloquea el acceso de inmediato (403/404).

Pilar C: Control de Acceso por Roles RBAC (OWASP A01)

Comprueba la estricta separación de privilegios: un token de Personal/Barbero no puede consultar reservas privadas de Clientes (401), ni crear nuevas barberías en la Plataforma SaaS (403).

Pilar D: Robustez Total de la API (105 Operaciones)

Certifica que la totalidad de los 105 métodos HTTP de la aplicación desplegada en Railway responden de forma segura y consistente bajo estrés, logrando una tasa de 0 fallas 500 (100% de robustez).

4. Guía Rápida para la Sustentación ante el Jurado

P: ¿Por qué en GitHub Actions ZAP muestra 1 alerta 'High' si el sistema es seguro?
R: La alerta corresponde a un componente cliente de Swagger UI (swagger-ui-bundle.js con DOMPurify 3.4.13), no a nuestro código de NestJS. En producción comercial, Swagger UI se desactiva mediante la variable SWAGGER_HABILITADO=false, dejando cero superficie expuesta.

P: ¿Por qué fue necesario hacer un script DAST con token?
R: Porque según el estándar OWASP (A01: Broken Access Control), las vulnerabilidades más críticas (BOLA, IDOR y escalamiento de privilegios) solo pueden detectarse simulando a un usuario autenticado que intenta violar los límites de su rol o de su barbería.

P: ¿Por qué el backend responde 400 Bad Request en lugar de 200 en las pruebas de inyección?
R: Porque el ValidationPipe con whitelist: true intercepta las cargas maliciosas antes de que lleguen a la base de datos. Un código 400 significa que el firewall de aplicación de NestJS defendió el sistema con éxito.

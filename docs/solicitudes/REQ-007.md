# REQ-007 — Validación de migraciones y de datos en la base de datos de desarrollo

## 1. Identificador y título

`REQ-007` — Verificar, contra MySQL 8.0 real, que el historial de migraciones aplica
limpio, que el esquema resultante es el esperado y que los datos de las dos barberías
siguen íntegros tras la aplicación.

## 2. Fecha y solicitante

- Fecha: 2026-10-21 (fecha del commit `ebbe832`).
- Solicitante: responsable de la ejecución backend del proyecto Barbería.

## 3. Objetivo

Cerrar la fase de aplicación de migraciones con evidencia observable: estado del
historial, estructura de las tablas afectadas, índices únicos, integridad referencial
entre negocios y comportamiento transaccional real de la reserva.

## 4. Alcance

Incluye: comprobación del estado de migraciones, inspección de columnas e índices,
conteos de datos, integridad de membresías y prueba de humo transaccional.

Fuera de alcance: cambios de esquema, escrituras permanentes en la base de datos de
desarrollo, y cualquier operación sobre `bd_barberia` o Railway.

## 5. Contexto y estado previo

`REQ-006` había añadido dos migraciones y dos columnas nuevas
(`idempotencyKey`, `gestionTokenCifrado`). Faltaba comprobar que el historial completo
aplica sin error sobre una base limpia, que los índices únicos derivados existen
realmente y que la lógica de negocio se comporta como se documenta frente a las
restricciones reales de MySQL (no solo frente a los dobles de prueba).

## 6. Requisitos funcionales

- RF-1. El historial completo de migraciones aplica sin error sobre la BD de desarrollo.
- RF-2. Las columnas y los índices esperados existen con el tipo y la unicidad correctos.
- RF-3. Los datos de las dos barberías se conservan íntegros.
- RF-4. No existen membresías ni reservas cruzando negocios.
- RF-5. La prueba de humo se ejecuta dentro de una transacción que se revierte.

## 7. Requisitos no funcionales

- RNF-1. Cero residuos: la prueba de humo no deja filas nuevas.
- RNF-2. Trazabilidad: cada comprobación se ejecuta con un comando y se registra su salida.
- RNF-3. No se ejecutan `prisma db push` ni `migrate reset`.

## 13. Pruebas

- Pruebas nuevas: ninguna en esta fase.
- Pruebas ejecutadas: `npm run db:migrate:status:dev`, `npm run db:migrate:dev`,
  `SHOW COLUMNS` / `SHOW CREATE TABLE` / `SHOW INDEX` sobre `reservations`, consultas de
  conteo e integridad, y la prueba de humo transaccional (CA-9 a CA-13) revertida al
  finalizar.
- Resultado: las 20 migraciones aplicadas; los 13 criterios de aceptación de la tabla
  anterior, con salida satisfactoria; la prueba de humo dejó la base de datos en el
  mismo estado (transacción revertida).

## 14. Riesgos y límites

- Límite: la verificación se hizo sobre MySQL 8.0.46 en el contenedor de desarrollo; otros
  motores o versiones pueden diferir en el comportamiento de los índices generados.
- Riesgo residual: la prueba de humo depende de la clave foránea de negocio en
  `reservations`; si alguien la elimina, CA-13 dejaría de detectar el cruce. Mitigación:
  la suite e2e de aislamiento negativo cubre ese caso.
- Límite: no se verificó el comportamiento de las migraciones sobre `bd_barberia` ni sobre
  Railway, por restricción del alcance.

## 15. Resultado y estado

**COMPLETADA.** El historial aplica limpio, el esquema es el esperado y los datos de
desarrollo están íntegros, con evidencia de cada comprobación.

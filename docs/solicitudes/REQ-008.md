# REQ-008 — Trazabilidad de solicitudes, documentación formal de API y auditoría de endpoints

## 1. Identificador y título

`REQ-008` — Crear el sistema de trazabilidad de solicitudes, documentar formalmente la API
real, auditar la suficiencia de endpoints y la consistencia entre reglas, código y
pruebas, y validar todo lo anterior.

## 2. Fecha y solicitante

- Fecha: 2026-10-21 (sin commit: la entrega es documental).
- Solicitante: responsable de la ejecución backend del proyecto Barbería.

## 3. Objetivo

Que cada solicitud de desarrollo procesada con OpenCode quede registrada de forma
formal y verificable, y que exista una referencia de la API **basada en el código real**
que permita responder «qué puede hacer el backend» y «qué le falta» sin leer los 15
controladores.

## 4. Alcance

Incluye: procedimiento y registros de trazabilidad, cabecera de trazabilidad en los
archivos de la fase, referencia formal de la API, auditoría de suficiencia de endpoints,
auditoría de consistencia y validación completa del resultado.

Fuera de alcance: **corregir** los hallazgos detectados (H-01 a H-06, G-01 a G-11): se
documentan, no se implementan. Tampoco se toca el frontend, ni Railway, ni la base de
datos.

## 5. Contexto y estado previo

- Existían 8 solicitudes previas procesadas con OpenCode (fases 11 a 16 y la revisión
  posterior) **sin ningún registro formal**: su rastro estaba solo en el historial de
  commits y en el `CONTRATOS_API_MULTITENANT.md`.
- `.gitignore` excluía `/docs/` por completo, de modo que la estructura de solicitudes
  propuesta (`docs/solicitudes/`) habría quedado **sin versionar**.
- La documentación de API era un **contrato de cambios** (qué rutas se rompieron y qué debe
  migrar el frontend), no un catálogo: de las 85 rutas del backend, el contrato solo
  describía las afectadas por las fases 9 a 16.
- No había ninguna auditoría que dijera si las reglas de negocio estaban cubiertas por la
  API ni si la documentación coincidía con el código.

## 6. Requisitos funcionales

- RF-1. Un procedimiento formal y versionado para registrar cada solicitud procesada con
  OpenCode, con secciones obligatorias y estados de ciclo de vida.
- RF-2. Un registro por solicitud previa (8 REQ) con las 15 secciones obligatorias.
- RF-3. Una cabecera de trazabilidad en los archivos creados o modificados por la fase.
- RF-4. Una referencia formal de la API real: método, ruta, autenticación, rol, cuerpo,
  respuesta y reglas específicas.
- RF-5. Una auditoría de suficiencia: regla de negocio → endpoints → estado, con huecos
  priorizados.
- RF-6. Una auditoría de consistencia: reglas documentadas ↔ código ↔ pruebas, con
  hallazgos verificables por fichero y línea.

## 7. Requisitos no funcionales

- RNF-1. **Veracidad**: ningún resultado, ruta o prueba afirmada sin comprobar; lo no
  ejecutado se declara como no ejecutado.
- RNF-2. **Versionado**: las carpetas de trazabilidad y de API deben quedar dentro del
  control de versiones, sin desterrar el resto de `docs/`.
- RNF-3. **No invasión**: esta fase no modifica `src/`, `test/`, `prisma/` ni el frontend.
- RNF-4. Las decisiones de diseño existentes se respetan: no se rediseña el modelo
  multitenant ni se cambian roles.
- RNF-5. Los documentos citan rutas y líneas verificables.

## 13. Pruebas

- Pruebas nuevas: ninguna (fase documental).
- Pruebas ejecutadas: `npm test`, `npm run test:multitenant`, `npm run test:e2e`,
  `npm run typecheck`, `npm run build`, `npx prisma validate`, `npx eslint` (resultado

- Resultado: `npm test` → 83 suites / 996 tests en exit 0;

  `prisma validate` en exit 0; `git diff --check` sin avisos.
- `npm run test:e2e` → **19 suites, 4 no cargan** (H-10). No es una regresión de esta fase:
  el defecto es previo y está documentado.
- Comprobaciones documentales: 85 rutas extraídas por script de los 15 controladores y
  contrastadas una a una con la referencia (0 ausentes, 0 fantasma); 84 operaciones
  contrastadas contra el OpenAPI real; 7 códigos de dominio contrastados entre contrato,
  código y pruebas.

## 14. Riesgos y límites

- Riesgo: cambiar `/docs/` por `/docs/*` altera el comportamiento de `git add docs/` para
  un archivo nuevo suelto en `docs/` (seguirá ignorado, que es lo que se quería). Verificado
  con `git check-ignore`.
- Riesgo: la referencia de API describe el estado **de hoy**; envejece si cambia el
  código. *Plan B*: regenerarla desde Swagger (`/api/docs-json`) en cada fase.
- Límite: la auditoría no comprueba el comportamiento en ejecución de las 85 rutas: se
  basa en la lectura del código, en las pruebas existentes y en la verificación en base de
  datos de la fase anterior.
- Límite: los hallazgos H-01 a H-10 y las brechas G-01 a G-11 **no están corregidos**;
  su corrección es una decisión posterior.
- Límite: el modelo ejecutor anotado es el del entorno actual; si cambia el modelo, las
  cabeceras de trazabilidad quedan desactualizadas.

## 15. Resultado y estado

**COMPLETADA.** El sistema de trazabilidad está creado y versionado, con 8 registros de
solicitud; la API está documentada desde el código (85 rutas, contrastadas con el OpenAPI
real); las auditorías de suficiencia y de consistencia están hechas con 11 brechas y 10
hallazgos; y la validación completa pasa sin errores en las suites que hoy funcionan
(`npm test` y `npm run test:multitenant`).

# REQ-002 — Paridad del historial de migraciones con `schema.prisma`

## 1. Identificador y título

`REQ-002` — Restaurar la paridad entre el esquema declarado (`prisma/schema.prisma`) y el
historial de migraciones versionado, usando una migración aditiva (no destructiva).

## 2. Fecha y solicitante

- Fecha: 2026-10-21 (fecha del commit `1ea3598`).
- Solicitante: responsable de la ejecución backend del proyecto Barbería.

## 3. Objetivo

Eliminar la divergencia entre el índice único declarado en `schema.prisma` sobre
`Administrador(negocioId, usuarioId)` y el historial de migraciones, de modo que una base
de datos creada desde cero y una base migrada converjan en el mismo esquema.

## 4. Alcance

Incluye: la migración aditiva que crea el índice único, la regeneración del cliente
Prisma y la verificación de paridad.

Fuera de alcance: reescribir o reescribir migraciones ya aplicadas; tocar `bd_barberia`;
cambios de modelo de datos en otras tablas.

## 5. Contexto y estado previo

`prisma/schema.prisma` declaraba un índice único en `Administrador` que ninguna migración
del historial creaba. Consecuencia: una base creada con `prisma migrate deploy` quedaba
sin ese índice, mientras el modelo en memoria sí lo asumía. Además, la animación de
"migración pendiente" de Prisma exigía un historial limpio.

## 6. Requisitos funcionales

- RF-1. El historial de migraciones debe producir exactamente el esquema de `schema.prisma`.
- RF-2. La corrección debe ser **aditiva**: no se reescribe ni se borra ninguna migración
  existente.
- RF-3. La detección de divergencia debe ser automatizada y repetible.

## 7. Requisitos no funcionales

- RNF-1. Cero escrituras sobre `bd_barberia` o Railway durante la corrección.
- RNF-2. La prueba de paridad debe correr sobre un MySQL 8.0 limpio.
- RNF-3. La migración debe ser reversible por *down* manual documentado.

## 8. Criterios de aceptación

| # | Criterio | Resultado verificado |
|---|----------|----------------------|
| CA-1 | Existe una migración que crea el índice único `Administrador(negocioId, usuarioId)` | Verificado: `prisma/migrations/20261023120000_agregar_indice_unico_administrador_negocio/migration.sql` |
| CA-2 | `prisma migrate status` no reporta divergencia | Verificado: salida sin divergencia en la BD de desarrollo |
| CA-3 | Una BD creada desde cero tiene el mismo esquema que una migrada | Verificado: `test/multitenant-historial-linux.e2e-spec.ts` |
| CA-4 | `prisma/seed.ts` sigue siendo compatible con el índice | Verificado: la suite unitaria de `seed` pasa en el barrido completo |

## 9. Archivos creados

- `prisma/migrations/20261023120000_agregar_indice_unico_administrador_negocio/migration.sql`.

## 10. Archivos modificados

- `prisma/schema.prisma` — se conserva la declaración del índice (sin cambios de modelo).
- `prisma/seed.ts` — adaptación al índice único.
- `test/multitenant-historial-linux.e2e-spec.ts` — se le añade la comprobación de paridad.
- `generated/prisma/internal/class.ts` — regeneración del cliente Prisma.

## 11. Archivos eliminados

Ninguno.

## 12. Dependencias

Ninguna.

## 13. Pruebas

- Pruebas nuevas: `test/multitenant-historial-linux.e2e-spec.ts` cubre la creación de la
  BD desde el historial completo y la comparación de esquema con `schema.prisma`.
- Pruebas ejecutadas: `npm run test:multitenant` (suite completa, incluye la de paridad) y
  `npm test`.
- Resultado: `npm run test:multitenant` → 17 suites / 150 tests en exit 0;
  `npm test` → 83 suites / 996 tests en exit 0.

## 14. Riesgos y límites

- Riesgo residual: si alguien edita `schema.prisma` sin añadir migración, la divergencia
  vuelve a aparecer. Mitigación: la prueba de paridad de CA-3 lo detecta.
- Límite: la comparación de esquema cubre tablas, columnas, índices y claves foráneas; no
  cubre diferencias de collation no declaradas en el modelo.

## 15. Resultado y estado

**COMPLETADA.** La divergencia está cerrada, la corrección es aditiva y la paridad queda
cubierta por una prueba automatizada.
